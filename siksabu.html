식사부장관 · 두 앱을 하나의 모노레포로

고객용 앱 하나로 시작한 프로젝트에 사장님용 앱이 추가되면서, 두 앱이 로그인·네트워크·디자인 시스템을 함께 쓰도록 구조를 바꾼 과정입니다.

기간2026.07 – 진행 중
내 역할Flutter 앱 전체 (저장소 커밋 29개 모두 본인)
협업REST API·인증 서버는 백엔드 팀
상태화면·서버 연동 진행 중, 배포 전

01서비스와 내가 맡은 일

식사부장관은 공단 근로자가 주변 식당을 찾고 식대 잔액으로 QR 결제하는 서비스입니다. 근로자는 고객용 앱에서 식당을 찾고 자신의 QR로 결제하며, 식당 사장님은 사장님용 앱에서 메뉴·가격을 관리하고 QR을 스캔해 결제를 받습니다.

  • 앱 구조 · 앱 2개와 공유 패키지 2개로 이루어진 Melos 모노레포를 설계했습니다.
  • 화면 · Figma 시안을 기준으로 고객용 13개, 사장님용 9개 기능 화면을 구현하고 있습니다.
  • API 연동 · Retrofit API 14개와 Dio 인터셉터, 공통 에러 처리를 만들었습니다.
  • 인증 · Keycloak 로그인(Authorization Code + PKCE)과 go_router 인증 가드를 구현했습니다.
  • 맡지 않은 일 · 서버 API와 인증 서버 설정은 백엔드 팀이 맡았습니다. 저는 API 규약을 맞추고 연동 중 생긴 문제를 정리해 전달했습니다.

02문제: 두 번째 앱이 생겼다

2026년 6월 23일부터 고객용 앱을 단일 Flutter 프로젝트로 개발했습니다. 7월 중순에는 기능 13개와 Keycloak 로그인, API 연동 로직까지 들어가 있었습니다. 이때 사장님용 앱이 필요해졌습니다.

두 앱이 같아야 하는 것 두 앱이 달라야 하는 것
  • Keycloak 로그인과 토큰 갱신
  • 같은 API 서버와 에러 응답 처리
  • 색상·글자·아이콘·버튼 (한 서비스로 보여야 함)
  • 식당·메뉴·식권 같은 공통 데이터 모델
  • 화면과 기능 (결제 vs. 메뉴 관리·결제 받기)
  • 앱 ID와 로그인 후 돌아올 주소
  • 라우팅과 하단 탭 구성

03다른 방법과 비교

방법 장점 문제
고객 앱을 복사해 사장님 앱 만들기 바로 시작할 수 있음 인증·네트워크 코드를 두 곳에서 고쳐야 하고, 시간이 지나면 두 앱의 처리 방식이 달라질 수 있음
한 앱에서 사용자 역할에 따라 화면 나누기 코드베이스가 하나 사장님 기능이 고객 앱에도 함께 들어가고, 앱 ID와 스토어 등록을 따로 할 수 없음
모노레포: 앱 2개 + 공유 패키지 공통 코드는 한 곳에서 관리하고, 앱은 따로 빌드·배포 초기 설정이 필요하고 패키지 경계 규칙을 지켜야 함

공통 코드를 한 곳에서 고치면서 두 앱을 따로 배포할 수 있는 방법이 모노레포라서 이 구조를 골랐습니다. 7월 16일 Dart pub workspace와 Melos 8로 전환했습니다.

04무엇을 공유하고 무엇을 분리했나

customer_app ─┬─→ siksabu_core ──→ siksabu_ui_kit
owner_app    ─┘   (앱은 ui_kit도 직접 사용)
위치 담은 것 기준
siksabu_core Dio 인스턴스·인터셉터, 에러 타입(Failure), 토큰 보안 저장소, 환경 설정, 두 앱의 공통 모델, Keycloak 인증 두 앱에서 똑같이 동작해야 하는 부분
siksabu_ui_kit 색상·글자·간격 토큰, 아이콘 경로 상수, 버튼·입력창·칩 같은 공통 위젯, 폰트 한 서비스로 보이게 하는 부분. Flutter와 flutter_svg에만 의존
각 앱 라우터와 인증 가드, 앱 전용 기능과 이미지 사용자 역할에 따라 달라지는 부분

경계를 지키기 위해 세 가지 규칙을 정했습니다.

  • 의존은 앱 → core → ui_kit 한 방향으로만 흐릅니다. ui_kit은 core를 모릅니다.
  • 앱끼리는 서로 import하지 않습니다. 두 앱이 모두 필요로 하면 공유 패키지로 올립니다. 식당 상세·식권 사용 모델도 이렇게 core로 옮겼습니다.
  • 패키지 내부 파일(src/)을 직접 import하지 않고, 패키지가 공개한 파일만 사용합니다.

설계 중에 생긴 순환 의존

처음에는 간격 값(AppSpacing)을 core에 두었습니다. 그런데 core의 인증 모듈은 ui_kit 테마를 쓰고, ui_kit 위젯은 core의 AppSpacing을 써서 두 패키지가 서로를 참조하게 됐습니다. 간격도 색상·글자처럼 디자인 토큰이라고 판단해 ui_kit으로 옮겼고, 그 결과 ui_kit은 다른 패키지에 의존하지 않게 됐습니다.

05불편했던 점과 대응

전환 직후 아이콘과 폰트가 사라졌다

모노레포로 옮긴 날 하단 내비게이션을 비롯한 SVG 아이콘이 모두 보이지 않았고, 폰트도 Pretendard가 아닌 기본 폰트로 바뀌어 있었습니다.

에셋을 ui_kit 패키지로 옮기면 번들 경로 앞에 packages/siksabu_ui_kit/이 붙습니다. 코드는 예전 경로를 그대로 불렀고, Flutter는 이 경우 예외 없이 아무것도 그리지 않아 바로 알아채기 어려웠습니다.

  • 아이콘 경로는 AppIcons 상수 한 곳에서만 만들고, 하드코딩된 경로 19곳을 이 상수로 바꿨습니다.
  • 폰트는 텍스트 스타일과 테마에 패키지 이름을 지정했습니다.
  • 앱 번들에서 아이콘이 실제로 로드되는지 확인하는 테스트를 추가했습니다. ui_kit 패키지 안에서 돌리는 테스트는 잘못된 경로도 파일을 찾아 통과시켜서, 이 검증은 앱 쪽에서 하도록 했습니다.

관련 커밋 보기

코드 생성과 의존성 설정이 패키지 단위로 나뉘었다

  • freezed·Retrofit 코드 생성은 패키지마다 따로 실행해야 합니다. core의 모델을 고치고 앱에서만 생성하면 반영되지 않습니다. 그래서 생성이 필요한 패키지를 한 번에 처리하는 melos run generate 스크립트를 만들었습니다.
  • 의존성 버전 고정(dependency_overrides)은 워크스페이스 루트에만 둘 수 있어, build_runner 호환을 위한 버전 고정을 루트로 옮겼습니다.
  • 이런 규칙은 README와 개발 규칙 문서에 적어 두었습니다.

06인증 가드와 토큰 갱신

두 앱의 로그인 흐름은 core의 인증 모듈을 함께 쓰고, 화면 이동 제한은 각 앱의 라우터가 맡습니다.

  • go_router redirect · 로그인 확인 중에는 스플래시에 머물고, 로그인된 상태로 스플래시·로그인 화면에 있으면 홈으로, 로그인되지 않았으면 로그인 화면으로 보냅니다.
  • 라우터를 다시 만들지 않기 · Riverpod의 로그인 상태를 ValueNotifier로 옮겨 go_router의 refreshListenable에 연결했습니다. 로그인 상태가 바뀌면 redirect만 다시 판단하므로 화면 스택이 유지됩니다.
  • 401 처리 · Dio 인터셉터가 401을 받으면 토큰을 갱신하고 원래 요청을 한 번만 다시 보냅니다. 여러 요청이 동시에 401을 받아도 갱신은 한 번만 실행되고, 다시 보낸 요청이 또 401이면 더 이상 갱신하지 않습니다.

백엔드 팀과 원인 범위 좁히기

로그인에 성공해 받은, 만료되지 않은 토큰으로 잔액 API를 호출했는데 계속 401이 돌아온 적이 있습니다. 토큰 갱신은 매번 성공해서 앱이 로그아웃되지도 않았고, 잔액 화면은 로딩과 에러를 반복했습니다. 한 번만 재시도하도록 막아 둔 덕분에 갱신 요청이 무한히 반복되지는 않았습니다.

토큰의 만료 시간과 갱신 결과를 직접 확인해, 토큰 발급이 아니라 서버의 토큰 검증 단계 문제일 가능성이 높다고 범위를 좁혔습니다. 재현 조건과 확인할 항목(계정 권한, 401과 403의 구분 등)을 문서로 정리해 백엔드 팀에 전달했습니다.

  • 현재 공유 패키지와 두 앱에 테스트 파일 10개가 있습니다(core 5, ui_kit 2, 고객용 앱 2, 사장님용 앱 1).

한계와 남은 일

  • 서버에 식당·식단 데이터가 아직 적어서, 목록 화면은 서버 응답에 예시 데이터를 덧붙여 보여 줍니다. 서버 호출이 실패하면 첫 페이지는 예시 데이터로 대신합니다. 데이터가 쌓이면 이 병합 코드를 지울 예정입니다.
  • 개발 편의를 위해 고객용 앱의 인증 가드에서 로그인하지 않은 사용자의 이동 제한을 임시로 풀어 두었습니다. 배포 전에 되돌려야 합니다.
  • 서비스 이름은 바꿨지만 앱 ID와 로그인 후 돌아올 주소는 인증 서버 설정과 맞춰야 해서 예전 이름을 유지하고 있습니다. 백엔드 팀과 함께 바꿀 예정입니다.
  • 모노레포는 설정 비용이 있습니다. 에셋을 추가하거나 모델을 옮길 때 지켜야 할 규칙이 늘어서, 이 규칙을 문서와 테스트로 관리하고 있습니다.
  • 아직 스토어에 출시하지 않았습니다.
